# MediaHub 稳定性审计与关键修复设计

日期：2026-05-12

## 目标

在不做无边界重构的前提下，对 MediaHub 当前前端、后端和联调整体做一次高强度稳定性审计，并允许对阻塞主流程的缺陷进行即时修复。首轮交付重点不是“做更多功能”，而是建立真实基线、收敛关键问题、明确后续重构和清理边界。

本轮目标按优先级排序：

1. 跑通桌面端与移动端核心用户路径。
2. 找出并修复 P0、P1 级问题中的阻塞项。
3. 区分“项目实现缺陷”和“外部公开 API 风险”，同时检查项目层是否缺少必要兜底。
4. 产出可执行的问题清单，为后续代码清理、结构优化和 README 重写提供依据。

## 范围

本轮只覆盖子项目一：`稳定性审计与关键修复`。

审计范围包括：

- 前端：路由、页面状态、交互按钮、错误态、空态、桌面端布局、移动端布局。
- 后端：健康检查、分类、内容列表、详情、推荐、用户、来源状态、手动刷新接口。
- 联调：前端请求链路、Cookie/用户态、来源刷新后的页面反馈、跨页面状态同步。
- 双基线检查：
  - 与 `需求文档_MediaHub.md` 的功能预期比对。
  - 与当前实际实现的行为和限制比对。
- 双归类检查：
  - 项目内部缺陷。
  - 外部公开 API 风险以及项目对这些风险的兜底缺口。

## 非目标

本轮不做以下事项：

- 不直接执行大范围目录重组或全面架构重写。
- 不扩展新业务能力，不新增与当前闭环无关的功能。
- 不把“未实现但需求中提到”的全部能力强行补齐。
- 不直接删除文件；若识别到无关文件或废弃文件，只先列清单，待用户确认后处理。
- 不为外部公开 API 的不稳定性背书；只负责项目侧的超时、错误提示、缓存、降级和可恢复性。

## 执行策略

### 方案选择

采用“稳定性审计冲刺”模式作为当前方案：

1. 先建立运行与验证基线。
2. 按真实用户路径做全链路审计。
3. 发现阻塞主流程的高优先级问题立即修复。
4. 其余问题沉淀为清单，避免审计阶段失控扩张。

该模式优于“先分层重构再验证”的原因是：当前项目同时依赖前端状态、后端聚合逻辑和外部公开 API，如果不先明确根因和优先级，直接重构会把回归风险与已有缺陷混在一起。

### 修复准入规则

审计期间允许边审边修，但必须满足以下规则：

- 只修复已经复现且已定位根因的问题。
- 优先修复 P0 和 P1 中阻塞用户主流程的问题。
- 每次修改保持最小化，避免顺手做无关重构。
- 每个修复都必须带回归验证，至少覆盖引发问题的接口、页面或交互路径。

## 审计流程

### 1. 建立基线

- 确认 `backend` 和 `frontend` 的启动状态。
- 执行后端测试、前端构建、前端静态检查。
- 记录当前是否存在“未启动即失败”“构建失败”“测试失败”“静态检查失败”的基础问题。

### 2. 后端审计

按接口维度审计以下能力：

- `GET /api/health`
- `GET /api/categories`
- `GET /api/contents`
- `GET /api/contents/:id`
- `GET /api/recommendations/for-you`
- `GET /api/users/me`
- `POST /api/users/register`
- `POST /api/users/logout`
- `POST /api/users/history`
- `GET /api/users/history`
- `POST /api/users/favorite`
- `GET /api/users/favorites`
- `GET /api/sources/status`
- `POST /api/ingestion/refresh`

每个异常都记录以下信息：

- 请求条件和参数。
- 返回码与返回体。
- 服务端日志或堆栈。
- 是否依赖外部 API。
- 根因定位与影响范围。

### 3. 前端审计

按页面和状态流审计以下能力：

- 首页初始加载。
- 分类切换。
- 搜索与清除。
- 排序切换。
- 加载更多。
- 来源状态展示与手动刷新。
- 内容卡片跳转详情。
- 详情页加载、返回、来源信息、关联内容。
- 登录、退出、已看、收藏。
- 个人中心历史与收藏切换。
- 错误态、空态、加载态是否稳定且可恢复。

### 4. 浏览器强测

双端覆盖：

- 桌面端 Chrome。
- 移动端窄屏视口。

核心用户路径：

1. 打开首页。
2. 切换分类。
3. 搜索内容并清除关键词。
4. 查看列表分页或加载更多。
5. 进入详情页并返回。
6. 登录用户。
7. 标记已看。
8. 收藏与取消收藏。
9. 进入个人中心查看历史和收藏。
10. 回到首页再次验证状态同步。

同时检查：

- 浏览器控制台报错。
- 请求失败与重试行为。
- 按钮是否可点击。
- 关键元素是否被遮挡。
- 文案与状态是否一致。

### 5. 回归验证

每完成一轮修复后，按影响范围重跑：

- 对应后端测试。
- 对应前端构建或静态检查。
- 对应接口调用。
- 对应页面用户路径。

最终至少完成一次端到端回归，确认关键路径仍可用。

## 问题分级

### P0

主流程不可用或高概率中断，例如：

- 首页无法打开。
- 关键接口返回 500 或前端崩溃。
- 详情页无法进入。
- 登录后关键操作完全失效。

### P1

主流程可进入但结果错误或体验严重受损，例如：

- 已看、收藏、历史状态不同步。
- 搜索结果不正确或分页异常。
- 移动端关键按钮不可触达或误触严重。
- 外部 API 失败后页面没有稳定降级。

### P2

不阻塞主流程但影响质量或后续维护，例如：

- 文案不一致。
- 重复代码和低价值抽象。
- 文档缺失或过时。
- 疑似无关文件、临时文件、废弃文件残留。

## 外部依赖归类规则

对于 TVMaze、Open Library、Jikan 等公开 API 引发的问题，统一做双归类：

1. 记录为“外部依赖风险”，描述其不稳定、限流、字段变化、超时或内容缺失。
2. 同时检查项目是否存在下列缺口，并视情况额外记录为“项目缺陷”：
   - 缺少超时控制。
   - 缺少错误提示。
   - 缺少缓存回退或 stale 标识。
   - 缺少空态兜底。
   - 缺少刷新后状态同步。

这样可以避免把外部问题完全算到项目头上，也避免把项目侧应有的容错责任推给外部服务。

## 输出物

本轮至少产出以下结果：

1. 一份审计结果文档，包含：
   - 问题编号
   - 优先级
   - 端别
   - 模块
   - 复现步骤
   - 期望结果
   - 实际结果
   - 根因
   - 修复状态
   - 后续建议
2. 已修复问题对应的代码修改。
3. README 重写所需的真实能力清单和已知限制清单。
4. 候选清理项清单，包括死代码、重复逻辑和疑似无关文件，但删除动作不在本轮自动执行。

## 验收标准

满足以下条件，才认为子项目一完成：

- 桌面端与移动端核心路径均完成至少一轮验证。
- 所有发现的 P0 问题都已处理或明确阻塞原因。
- 已发现的 P1 问题完成分级和归因，能修的已修，暂不修的有理由。
- 关键修复项完成对应回归验证。
- 审计结果文档可直接作为后续“代码清理与结构收敛”以及“README/文档更新”的输入。

## 后续子项目

子项目一完成后，再进入以下工作：

1. `代码清理与结构收敛`
   - 根据已确认的问题清单，做小而确定的结构优化。
   - 删除无关文件前先提交候选列表给用户确认。
2. `README 与项目文档更新`
   - 以真实可运行能力为准，补齐启动、测试、目录结构、限制和后续计划。

## 工程原则

- KISS：优先最直接、最可验证的修复路径。
- YAGNI：不在审计阶段引入无关功能和复杂抽象。
- DRY：对重复的错误处理、状态处理和接口行为做定向收敛。
- SOLID：保持页面、接口、服务和存储职责边界清晰，修复根因而非表层症状。
